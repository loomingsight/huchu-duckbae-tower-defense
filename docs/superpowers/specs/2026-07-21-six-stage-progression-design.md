# 6스테이지 진행 및 난이도 설계

## 상태

- 사용자 승인: 2026-07-21
- 대상: 기존 스테이지 1에 신규 스테이지 5개 추가
- 검증 정책: E2E 제외, 단위 테스트·타입 검사·프로덕션 빌드로 검증

## 목표

1. 기존 스테이지 1을 포함해 총 6개 스테이지를 제공한다.
2. 각 스테이지는 타워·골드·창고 내구도를 초기화하는 독립 게임으로 동작한다.
3. 신규 몬스터·타워·이미지 에셋 없이 기존 콘텐츠를 재조합한다.
4. 모든 스테이지는 20×10 격자, 좌측 입구→우측 창고, 직각 단일 경로, 10웨이브를 유지한다.
5. 난이도의 주된 차이는 맵 압박과 적 조합으로 만들고 체력·속도 증가는 완만하게 제한한다.
6. 현재 코드의 스테이지 1 하드코딩을 최소한의 데이터 기반 구조로 일반화한다.

## 범위에서 제외

- 신규 몬스터, 타워, 투사체, 맵 이미지 및 Blender 에셋
- 분기 경로, 다중 입구, 금지 지형 및 새로운 배치 규칙
- 타워 업그레이드, 스테이지 간 타워·골드 승계
- 동적 난이도 보정, 무작위 웨이브 생성
- 점수 공식과 별 등급 기준 변경
- 신규 스테이지 선택 페이지와 화면 전환 애니메이션
- Playwright 및 기타 E2E 실행

## 공통 게임 규칙

- 시작 골드: `320G`
- 창고 내구도: `20`
- 웨이브 수: `10`
- 타워 가격·공격력·사거리·공격 주기: 기존 값 유지
- 몬스터 기본 체력·기본 속도·처치 보상·누출 피해: 기존 값 유지
- 웨이브 내 체력 증가: zero-based 웨이브 인덱스마다 `8%`
- 미노타우르스: 각 스테이지 10웨이브에 정확히 1마리
- 스테이지 클리어 시에만 다음 스테이지 순차 해금
- 재도전 및 다른 스테이지 시작 시 타워·골드·내구도 완전 초기화

적의 최종 체력과 이동량은 다음 계약을 따른다.

```text
최종 HP = 기본 HP × stage.hpMultiplier × (1 + waveIndex × 0.08)
이동량 = 기본 속도 × stage.speedMultiplier × slowMultiplier × dt
다음 스폰 대기 = waveGroup.spawnInterval × stage.spawnIntervalMultiplier
```

처치 보상에는 스테이지 배율을 적용하지 않는다.

## 맵 설계

모든 웨이포인트는 좌우 또는 상하로만 연결한다. 공통 맵 팩터리는 웨이포인트 사이를 1칸 단위로 확장하고 중복 경로, 경계 이탈 및 대각선 연결을 거부한다. 타워는 기존 정책대로 경로와 Chebyshev 거리 1인 비경로 칸에만 배치할 수 있다.

| ID | 웨이포인트 | 이동 칸 | 초기 배치 가능 칸 |
|---:|---|---:|---:|
| 1 | `(0,2)→(5,2)→(5,7)→(12,7)→(12,3)→(19,3)` | 28 | 58 |
| 2 | `(0,7)→(6,7)→(6,3)→(13,3)→(13,7)→(19,7)` | 27 | 56 |
| 3 | `(0,1)→(7,1)→(7,5)→(13,5)→(13,2)→(19,2)` | 26 | 54 |
| 4 | `(0,8)→(5,8)→(5,5)→(11,5)→(11,2)→(19,2)` | 25 | 52 |
| 5 | `(0,2)→(9,2)→(9,6)→(19,6)` | 23 | 48 |

스테이지가 올라갈수록 이동 경로와 배치 가능 영역을 함께 줄인다. 기존 잔디·길·입구·간식 창고 에셋과 원근 투영을 그대로 사용하며 맵별 신규 렌더 분기는 만들지 않는다.

## 최소 데이터 구조

```ts
type StageId = 1 | 2 | 3 | 4 | 5 | 6;

type StageDefinition = Readonly<{
  id: StageId;
  name: string;
  map: StageMap;
  waves: readonly Wave[];
  hpMultiplier: number;
  speedMultiplier: number;
  spawnIntervalMultiplier: number;
}>;
```

`STAGE_CATALOG`이 유일한 스테이지 정의 원본이다. `GameState`에는 직렬화 가능한 `stageId`만 추가하고 각 시스템은 `getStageDefinition(stageId)`로 동일한 정의를 조회한다.

`createStageMap(waypoints)`가 경로 확장, 도로 인접 판정, 배치 유효성 및 배치 가능 칸 나열을 공통 제공한다. 기존 `STAGE_1`과 `STAGE_1_WAVES` export는 스테이지 1 정의를 가리키는 호환 별칭으로 유지해 기존 소비자를 한 번에 깨뜨리지 않는다.

## 시뮬레이션 연결

- `createGame(stageId = 1)`: 유효한 스테이지 ID를 저장하고 항상 `320G`, 내구도 `20`, 빈 타워 배열로 시작
- `updateWaves`: 현재 스테이지의 10개 웨이브와 스폰 간격 배율 사용
- `spawnEnemy`: 현재 스테이지 HP 배율과 기존 웨이브 8% 배율 적용
- `updateEnemies`: 현재 맵 경로 길이와 스테이지 속도 배율 사용
- `updateGame`: 현재 스테이지 웨이브 수로 클리어 판정
- `placeTower`·`validateTowerPlacement`: 현재 스테이지 맵 사용
- 타게팅·경로 보간·맵 렌더·배치 가이드: `game.stageId`로 조회한 같은 맵 사용
- 투영, 사거리, 투사체, 폭발, 타워 전투 계산은 변경하지 않음

렌더링과 시뮬레이션이 서로 다른 맵을 조회하지 않도록 모든 진입점은 `GameState.stageId`를 기준으로 한다. 전역 mutable active-stage 값은 두지 않는다.

## 스테이지 선택과 진행 UI

기존 상태 오버레이 패널 안에 1~6 번호 버튼을 한 줄로 추가한다. 별도 페이지는 만들지 않는다.

- 준비·승리·패배 상태에서만 스테이지 선택기 표시
- 해금된 버튼만 선택 가능하고 현재 선택은 강조
- 앱 시작 시 가장 높은 해금 스테이지를 기본 선택
- 잠긴 버튼은 `disabled`와 `aria-label="스테이지 N 잠김"`을 함께 적용
- 준비 화면 주 버튼: `게임 시작`
- 패배 화면 주 버튼: 선택 상태를 바꾸지 않고 `다시 도전`
- 스테이지 1~5 승리 화면 주 버튼: 다음 스테이지를 선택한 뒤 `다음 스테이지`
- 스테이지 6 승리 화면 주 버튼: 같은 스테이지에서 `다시 하기`
- 플레이 HUD 웨이브 표기: `S2 · 3/10`

플레이 도중 스테이지를 바꾸는 조작은 제공하지 않는다. 스테이지 선택은 게임 상태를 즉시 변경하지 않고 다음 `startGame()`이 선택된 ID로 새 상태를 만들게 한다.

## 저장 데이터와 이전

저장 키를 `huchu-defense.preferences.v3`로 올리고 다음 최소 필드만 추가한다.

```ts
type StageRecord = Readonly<{
  bestScore: number;
  bestClearSeconds: number | null;
}>;

type GamePreferencesV3 = Readonly<{
  muted: boolean;
  totalAttempts: number;
  totalVictories: number;
  highestUnlockedStage: StageId;
  stageRecords: Partial<Record<StageId, StageRecord>>;
}>;
```

- v2의 `bestScore`와 `bestClearSeconds`는 스테이지 1 기록으로 이전
- v2의 `totalVictories > 0`이면 스테이지 2까지, 아니면 스테이지 1만 해금
- 승리 시 현재 스테이지 기록을 갱신하고 `min(6, stageId + 1)`까지 해금
- 패배 시 최고 점수만 갱신하고 최단 클리어 시간과 해금 상태는 유지
- 별 수는 기존 점수 공식에서 다시 계산할 수 있으므로 저장하지 않음
- 잘못된 ID, 음수·비유한 기록, 손상된 JSON은 안전한 기본값으로 정규화
- localStorage 읽기·쓰기가 실패해도 앱 메모리의 현재 preferences를 갱신해 같은 세션에서는 다음 스테이지 진행 가능

전체 도전·승리 횟수는 기존처럼 전역 누적하고 최고 점수·최단 시간은 현재 스테이지 기록을 결과 화면에 표시한다.

## 점수 정책

기존 점수 공식과 별 기준 `7,000 / 10,000점`을 유지한다. 모든 스테이지가 10웨이브이고 총 적 수가 161~183 범위이므로 기존 처치·웨이브·내구도·보스·시간 점수 구조를 재사용한다. 이번 범위에서는 난이도 보너스나 스테이지별 별 기준을 추가하지 않는다.

## 오류 및 경계 조건

- 유효하지 않은 `stageId`는 스테이지 1로 정규화한다.
- 맵 웨이포인트가 경계를 벗어나거나 대각선·중복 경로를 만들면 맵 팩토리가 명시적으로 거부한다.
- 비어 있거나 잘못된 웨이브 그룹은 기존 안전 검증으로 건너뛴다.
- 잠긴 스테이지 선택은 disabled UI뿐 아니라 선택 함수에서도 거부한다.
- 마지막 스테이지 승리 시 해금 값은 6을 넘지 않는다.
- localStorage가 없거나 quota 오류가 발생해도 게임 시작·재도전·세션 해금은 계속 동작한다.
- 스테이지 변경으로 남아 있던 투사체·효과·선택 타일은 새 게임 생성과 함께 초기화한다.

## 테스트 및 검증

### 단위 테스트

1. 카탈로그가 ID 1~6을 중복 없이 포함하고 잘못된 ID는 1로 정규화하는지 검증
2. 각 맵이 20×10, 좌측 시작·우측 종료, 직각 인접·중복 없는 경로인지 검증
3. 맵별 이동 칸과 초기 배치 가능 칸이 `28/58`, `27/56`, `26/54`, `25/52`, `23/48`, `22/46`인지 검증

### 실행 검증

- `npm run check`: 전체 Vitest, TypeScript, Vite 프로덕션 빌드
- 빌드된 `dist/index.html`의 `/huchu-duckbae-tower-defense/` base 확인

- 실제 난이도 미세 조정은 배포 후 사용자 플레이 피드백을 별도 백로그로 처리

## 최소 구현 순서

1. 공통 맵 팩토리와 6개 스테이지·웨이브 카탈로그 추가
2. `GameState.stageId`를 통해 시뮬레이션·배치·타게팅·렌더를 현재 스테이지에 연결
3. 기존 오버레이에 번호 선택기와 순차 해금·다음 스테이지 동작 추가
4. preferences v3 이전과 스테이지별 기록 추가
5. 단위 테스트와 `npm run check`로 검증

이 순서는 에셋 작업과 신규 의존성을 만들지 않고 데이터와 기존 함수의 입력만 일반화한다.

## 완료 조건

1. 스테이지 1~6을 선택하고 각기 다른 직각 단일 경로에서 플레이할 수 있다.
2. 모든 스테이지는 10웨이브이며 승인된 적 조합과 난이도 배율을 사용한다.
3. 클리어해야 다음 스테이지가 열리고 새 스테이지는 자원과 타워가 초기화된다.
4. 잠금 상태와 스테이지별 최고 점수·최단 시간이 재접속 후 유지된다.
5. 기존 이미지 에셋, 타워, 몬스터, 투영 및 전투 표현을 그대로 재사용한다.
6. 전체 단위 테스트·타입 검사·프로덕션 빌드가 통과한다.
7. E2E를 실행하지 않았다는 사실을 최종 결과에 명시한다.
